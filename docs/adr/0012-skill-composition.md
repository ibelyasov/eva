# У каждого действия один ответственный скилл

`eva-tasks` отвечает за задачи, проекты, Inbox и обзоры в SingularityApp; `eva-habits` — за эксперименты, отметки, области и Ритуалы в Habitify; `eva-calendar` — за вид календарей, События и Распорядок в Google Calendar; `eva-planning` — за План дня, вместимость Фокус-листа и Брони; `eva-notes` — за Хранилище Obsidian: вики знаний, дневник, захват и ответы по базе ([ADR 0018](0018-notes-over-llm-wiki.md)); `eva` — всегда загруженный навигатор: карта скиллов, справка по запросу, карта команд, словарь, объявление ключей предпочтений ([ADR 0017](0017-declarative-preferences.md)), Журнал Eva и Инициатива ([ADR 0022](0022-eva-journal-and-initiative.md)). У каждого действия один явный ответственный. Перед записью в чужого провайдера или в Хранилище скилл загружает скилл-владельца по голому имени через `skill_view` и читает его `references/write-policy.md` через `skill_view(..., file_path=…)`, затем применяет эти правила; чужие правила не пересказывает. Это сохраняет один источник политики для каждой операции ([досье композиции](../../research/agents/skill-composition.md)).

Ссылки идут от `eva-planning` и `eva` к провайдерным скиллам. От навигатора доменные скиллы читают только два справочника: `skill_view(name="eva", file_path="references/initiative.md")` — правила Инициативы, сообщений, лимита и переходов — и `references/notebook.md` — форму записей Журнала Eva; остальные файлы `eva` они не пересказывают и не загружают. Свои записи в Журнал — Пометки, Наблюдения, Практики, строки Ленты — каждый скилл пишет по `notebook.md`, а не по правилам записи `eva-notes`: Журнал — служебная зона, а не заметки Хранилища ([ADR 0019](0019-vault-write-consent.md)). `description` может назвать соседний скилл только для различения при выборе, например «План дня с задачами ведёт eva-planning». Переход после завершённой практики к связанной практике другого скилла — явная передача по имени: `eva-tasks` после Daily open предлагает План дня `eva-planning` с одной фразой «зачем». Между провайдерными скиллами и `eva-notes` допускаются явные передачи: `eva-tasks` → `eva-calendar` для встречи из Inbox, `eva-habits` → `eva-calendar` для смены времени Ритуала с блоком Распорядка, любой скилл → `eva-tasks`, если запрос является задачей. `eva-tasks` → `eva-notes` переносит Идею и Справку из Inbox в Хранилище ([ADR 0008](0008-cancel-instead-of-delete.md)). `eva-notes` → `eva-habits` или `eva-tasks` читает ID привычки или проекта для Заметки и записывает у провайдера обратную ссылку на неё ([ADR 0021](0021-provider-back-links.md)). «Запиши …» без явного места распределяется по смыслу: обязательство — в Inbox через `eva-tasks`; идея, мысль, ссылка, файл или справка — в Хранилище через `eva-notes`; неясное — в Inbox ([ADR 0020](0020-ideas-in-daily-notes.md)). Передача не считается состоявшейся без фактической загрузки скилла через `skill_view`. Формулировка «для операций SingularityApp/Habitify используй …» ограничивает операции конкретного провайдера и не запрещает композицию.

## Consequences

Хранилище в этих правилах, кроме Журнала Eva, — такое же место записи, как провайдер; Read-back Хранилища — `read_file` записанного файла, а состав разбора утверждается Планом сущностей ([ADR 0019](0019-vault-write-consent.md)). Полная явная команда на два провайдера выполняется в обоих последовательно без дополнительного подтверждения, с Read-back после каждой записи, остановкой на первой ошибке и отчётом applied/unverified/unapplied, без автоматического отката. Исключение для безвозвратных операций Habitify задаёт [ADR 0014](0014-confirmations.md). Набор изменений на двух провайдерах, собранный агентом, требует одного общего Preview и одного подтверждения, а затем того же порядка исполнения. При недоступности скилла-владельца или его инструментов агент называет невыполненную часть, не имитирует передачу и результат.
