# Контракт разработки JediKit

JediKit содержит шесть русскоязычных Agent Skill для Hermes Agent: `jedikit-tasks` для SingularityApp, `jedikit-habits` для Habitify и ритуалов, `jedikit-calendar` для Google Calendar, `jedikit-planning` для Плана дня, `jedikit-notes` для Хранилища Obsidian владельца — вики знаний поверх встроенного Hermes `llm-wiki` — и `jedikit` для карты скиллов, навигации и объявления предпочтений. Пользовательские инструкции, обсуждения, коммиты и PR пишем по-русски; identifiers, команды и API сохраняем оригинальными.

Правила разработки живут только в этом файле; `CLAUDE.md` и другие копии правил не создавай.

## Источники истины и карта репозитория

Перед изменением прочитай [CONTEXT.md](CONTEXT.md) и относящиеся к задаче [ADR](docs/adr/). CONTEXT задаёт термины и модель, ADR — принятые решения, `skills/` — действующие инструкции. Не переоткрывай принятые решения по собственной инициативе. Если два действующих решения противоречат друг другу, останови затронутую работу и сообщи владельцу с точными ссылками; рутинные детали решай самостоятельно.

| Путь | Назначение |
| --- | --- |
| `skills/jedikit-*/`, `skills/jedikit/` | Единственный источник инструкций и справочных материалов шести скиллов |
| `skills/*/tools.json` | Машиночитаемый контракт инструментов: MCP-операции провайдерных скиллов и встроенные toolsets Hermes у `jedikit-notes` (ключ `toolset`); у `jedikit-planning` и `jedikit` его нет |
| `README.md` | Назначение, подключение к Hermes, требования к нему и раздел «Setup» для Потребителя |
| `CONTEXT.md`, `docs/adr/` | Единый словарь и решения |
| `research/` | Основания, контракты провайдеров и Hermes, реестр источников `research/sources.md` |
| `BACKLOG.md` | Отложенные возможности и явные исключения |
| `.github/workflows/check.yml` | Статические проверки в CI |
| `LICENSE`, `THIRD-PARTY-NOTICES.md` | MIT оригинальных материалов и права третьих лиц |
| `.work/` | Игнорируемые Git временные планы и результаты проверок |

Текущий контракт описывай в канонических документах, временный план — в `.work/`. Канонические документы описывают только то, что есть сейчас: без истории версий, «прежде/теперь» и дат принятия решений. Датированное provenance внешних источников остаётся в `research/`. Используй термины CONTEXT в предложениях, исследованиях и сценариях проверки.

## Граница с потребителем

JediKit задаёт, что и как Hermes делает в личной жизни и работе владельца по методологии каждой темы; сейчас это личная продуктивность. Потребитель — репозиторий clanwright: он подключает JediKit к Hermes Agent владельца. Hermes Agent — Хост: загружает скиллы и их `references/` и вызывает инструменты. На стороне потребителя выбор, подключение и реализация инструментов и MCP по контракту, окружение и песочница Hermes, включая монтирование Хранилища, `WIKI_PATH`/`OBSIDIAN_VAULT_PATH` и синхронизацию Хранилища, доступы, значения предпочтений в `skills.config` и `skills.auto_load` навигатора ([ADR 0017](docs/adr/0017-declarative-preferences.md)), приглашения к обзорам в cron и их доставка ([ADR 0003](docs/adr/0003-no-unattended-writes.md)), характер Hermes (`SOUL.md`) и его еженедельное самообучение, всё, что работает без модели, включение скиллов и развёртывание ([ADR 0016](docs/adr/0016-consumer-boundary.md)).

- Потребитель читает только `README.md`, включая раздел «Setup», и `tools.json` закреплённой ревизии. README на верхнем уровне объясняет, что есть в JediKit, зачем, что нужно от Hermes и какие предпочтения и приглашения задать при подключении.
- Нужен инструмент, которого у Hermes нет, — добавь ожидание в `tools.json` или в раздел README «Что нужно от Hermes». Реализацию, подключение, доступы и развёртывание не делай ни в JediKit, ни в репозитории потребителя.
- Задачи от потребителя приходят issue в этот репозиторий и передают рамку, а не спецификацию скилла: детали поведения уточняй у владельца в JediKit. Сам не создавай issues и не ссылайся на них из документов.

## Авторинг и границы

- В каждом `SKILL.md` обязателен YAML frontmatter с `name` (kebab-case, совпадает с каталогом) и `description` (когда выбирать скилл, без пересказа процедуры). Файл — не более 7000 байт UTF-8: это компактная точка входа, подробности живут в references. Основной текст даёт наблюдаемый результат; подробности выносятся в локальные `references/`.
- Один корневой `skills/`; без generated copies, вложенных пакетов и manifests. Hermes подключает его каталогом через `skills.external_dirs`, навигатор `jedikit` — ещё через `skills.auto_load` ([ADR 0005](docs/adr/0005-hermes-host-connections.md), [ADR 0011](docs/adr/0011-navigator-always-loaded.md)).
- Авторинг под Hermes: frontmatter только `name` и `description`; у `jedikit` ещё `metadata.hermes.config` с ключами контракта предпочтений ([ADR 0017](docs/adr/0017-declarative-preferences.md)), других расширений `metadata.hermes` нет. Frontmatter должен быть валидным YAML: значение `description` пиши в двойных кавычках, без неэкранированных `"` внутри. При невалидном YAML Hermes молча разбирает frontmatter построчно и теряет вложенный `metadata`. Первые 57 символов `description` попадают в индекс скиллов и должны различать скилл. Файлы скилла читаются `skill_view(name="<скилл>", file_path="references/<file>.md")` или `file_path="tools.json"`: Markdown-ссылка файл не загружает, `../` запрещён, соседний скилл загружается голым именем `skill_view(name="jedikit-calendar")`.
- Скиллы устанавливаются отдельно: нужные правила пересказывают в своих `references/` и не ссылаются на `docs/`, `CONTEXT.md`, `research/` или файлы других скиллов, кроме обязательных `SKILL.md`, `references/write-policy.md`, `references/tools.md` и `tools.json` скилла-владельца. Какие досье лежат под каким скиллом, показывает [research/README.md](research/README.md). Другой скилл называют по имени; правила записи владельца читают перед операциями с его провайдером или Хранилищем. Связи и явные передачи — по [ADR 0012](docs/adr/0012-skill-composition.md).
- Только инструкции, `tools.json` и документы. `tools.json` — декларативные данные, а не код. Не добавляй собственный код, скрипты, генераторы, MCP/proxy/runtime, MCP-декларации или инфраструктуру модельных проверок. Пробел в штатной проверке сообщай владельцу; новый код требует отдельного решения ([ADR 0004](docs/adr/0004-no-custom-code.md)).
- Подключения даёт Hermes. SingularityApp — официальный hosted MCP на сервере `singularity`; Habitify — операции хоста по бизнес-контракту REST/OpenAPI v2, с ключом только у доверенного адаптера хоста ([ADR 0001](docs/adr/0001-habitify-via-rest.md)); Google Calendar — инструменты сервера `google_calendar` ([ADR 0009](docs/adr/0009-separate-calendar-skill.md)). Официальный Habitify MCP не используется. Хранилище Obsidian — встроенные toolsets Hermes `file`, `terminal` и `web` в песочнице и встроенные скиллы `llm-wiki` и `obsidian`: `jedikit-notes` загружает их `skill_view` и дополняет переопределениями текстом, не копируя и не меняя ([ADR 0018](docs/adr/0018-notes-over-llm-wiki.md)). Пакет не объявляет MCP и секреты. Подключения, toolsets, `skills.config` и cron настраивает потребитель (см. «Граница с потребителем»).
- `skills/*/tools.json` (`version: 2`) у провайдерных скиллов задаёт у каждого инструмента сервер, базовое имя без префикса `mcp__<server>__` и `access: read | write`; у Habitify и Google Calendar ещё `required`. Habitify: чтения — сервер `habitify_read`, записи — `habitify`; Google Calendar — `google_calendar`. У `jedikit-notes` инструменты встроенные: вместо `server` ключ `toolset` (`file`, `terminal`, `web`, `skills`, `clarify`), имя вызывается без префикса, `access: read | write`, `required` нет; `optional: true` у инструмента, без которого работает часть сценариев (`web_extract`, `skills_list`). Имена — внешний контракт с Hermes: меняй их только вместе со скиллом и отмечай изменение в release notes. При нехватке инструментов скилл называет недостающие базовые имена и рекомендует подключить их в Hermes; сам ничего не устанавливает и не настраивает.
- Все блокирующие пробелы полей собираются одним вопросом `clarify` со свободным ответом; известное, необязательное и относительные даты не переспрашиваются. Глубокое уточнение намерения — через внешний скилл `grill-me` (`skills_list`, затем `skill_view`). Если он недоступен, назови его и рекомендуй установить в Hermes, без собственного интервью ([ADR 0013](docs/adr/0013-clarification.md)).
- Записи: полная явная команда, в том числе несколько названных записей на разных провайдерах, — сразу; одиночное предложение агента — одна строка и «да», собранный агентом набор — один общий Preview и подтверждение; согласие — карточка `clarify` «Да»/«Нет», timeout и пропуск не согласие. Безвозвратная потеря данных Habitify (удаление привычки, области, удаление/отмена отметок) всегда требует однострочного подтверждения. Однозначное удаление События — сразу; в отчёте укажи 30 дней в корзине Google и восстановление только в интерфейсе. Группа — последовательно, стоп на первой ошибке, отчёт applied/unverified/unapplied, без автоматического отката; после каждой записи Read-back ([ADR 0014](docs/adr/0014-confirmations.md)). Хранилище — отдельный вид согласия: явная просьба, включая массовую правку, — сразу и целиком; разбор материала — после Плана сущностей, ответ на который — свободный текст `clarify` без вариантов, без ответа записи нет; после каждой записи проверка `read_file` и отчёт сделано / не проверено / не сделано, без отката — его даёт Git Хранилища; слова владельца (`origin: owner`) не переписываются, Заметки из Hold не меняются; каждую запись в `AGENTS.md` Хранилища (список Hold) Hermes подтверждает кнопкой approval, отказ — «не сделано» без повтора и обхода через `terminal` ([ADR 0019](docs/adr/0019-vault-write-consent.md)). Фоновые запуски только читают и в Хранилище не пишут ([ADR 0003](docs/adr/0003-no-unattended-writes.md)).
- Предпочтения скиллы читают из блока `jedikit` и не записывают; просьбу их изменить передают Потребителю ключом и значением ([ADR 0017](docs/adr/0017-declarative-preferences.md)). Hermes `memory` хранит только пометки объектов — Режимы поддерева и Ритуалы с первой привычкой; скилл-владелец спрашивает пометку, когда её не хватает сценарию ([ADR 0006](docs/adr/0006-memory-holds-object-marks.md)). `jedikit-notes` `memory` не использует: оформление Хранилища — в его `SCHEMA.md`, список Hold — в его `AGENTS.md`. Скиллы не создают и не меняют задания cron ([ADR 0003](docs/adr/0003-no-unattended-writes.md)). Kanban исключён ([ADR 0007](docs/adr/0007-no-kanban.md)). Идею и Справку из Inbox `jedikit-tasks` переносит через `jedikit-notes`: Идею — строкой с `#идея` в заметку дня за дату создания Inbox item, Справку — захватом: источник в `Источники/…` или адресная Заметка, Входящие хранилища — если адрес неясен. «Перенеси и отмени» — запись, проверка `read_file`, затем `task_cancel` и Read-back сразу; «перенеси» — запись и проверка, затем одна строка «Отменить Inbox item <ID>?». После ручного переноса владельцем команда «перенёс, отмени» отменяет исходный Inbox item через `task_cancel` сразу; одно «перенёс» вызывает предложение отменить. При передаче встречи `jedikit-calendar` отмена возможна только после успешного создания и Read-back События. Отмена всегда только после подтверждённой записи на новом месте ([ADR 0008](docs/adr/0008-cancel-instead-of-delete.md), [ADR 0020](docs/adr/0020-ideas-in-daily-notes.md)). Обратную ссылку на Заметку о привычке или проекте (`Obsidian: <путь без .md>` и, при заданном `jedikit.notes.vault_name`, URI `obsidian://open`) пишут `jedikit-habits` и `jedikit-tasks` по своим правилам записи, когда Заметка создаётся по просьбе владельца; при `jedikit.habits.names = neutral` или незаданном ключе у чувствительной привычки в Habitify её не пишут; существующий текст сохраняется, массовой простановки нет ([ADR 0021](docs/adr/0021-provider-back-links.md)). Off Mode отсутствует в API Habitify: только инструкция для приложения, команды `off` нет.
- Сохраняй чужие изменения. Не включай в файлы или логи секреты и личные данные провайдеров. Provider, DNS, ACME, deploy, backup-writer, restore, prune, credential и secret mutations требуют явного разрешения владельца.

## Проверки и доказательства

Проверки из корня, без аккаунтов провайдеров:

```sh
git diff --check "$(git hash-object -t tree /dev/null)" HEAD  # всё дерево HEAD, как в CI
git diff --check HEAD                                         # незакоммиченные правки
```

- У Hermes v0.21.6 нет штатной проверки frontmatter, security scan и discovery для каталога `skills.external_dirs`: `hermes plugins validate` и `doctor` требуют plugin manifest. Валидность YAML frontmatter, состав `metadata.hermes.config`, inventory шести скиллов и отсутствие опасного содержимого проверяет независимое ревью ([ADR 0004](docs/adr/0004-no-custom-code.md)).
- Не заменяй недостающие проверки Python helper, fake manifest или собственной assertion logic.
- CI использует официальные инструменты с версиями и SHA из `.github/workflows/check.yml`, без моделей и provider accounts.

Проверка изменений — `git diff --check` и независимое ревью агентом. Модельных прогонов нет. Сохраняй читаемый вывод каждой проверки, команду, exit status и длительность в `.work/`. Отчёт завершения: изменённые пути, выполненные проверки и ссылки на вывод, непроверенные слои и риски. Статика, загрузка, поведение модели, авторизация провайдеров и запись/Read-back — разные результаты. Владелец пользуется скиллами и сообщает о проблемах; обязательного ручного runtime-гейта нет. Публикация версии (тег и GitHub release) — отдельное решение владельца.

## Исследования

Для вопросов о синтаксисе, настройке, версиях и поведении CLI/API сначала проверь установленную версию, локальную справку/source и `research/`; затем текущую официальную документацию или официальный `llms.txt`. Для обычного редактирования документов внешний поиск не нужен.

Каждый проверяемый тезис сопровождай первичной ссылкой и датой доступа; для реализации сохраняй version/commit pin. Различай заявления vendor, независимое чтение source, локально выполненную проверку и anecdote. Недоступный источник и непроверенный runtime явно оставляй неопределёнными. Авторские положения Дорофеева отделяй от академических выводов и продуктовых решений; расхождение с автором выноси владельцу. Сохраняй provenance в `research/sources.md`, формулируй самостоятельно, не копируй книги и чужие ассеты. Правовые основания — `research/legal-and-attribution.md`.

## Коммиты

Сообщение коммита по-русски по шаблону `.github/COMMIT_TEMPLATE.md`; обязательная атрибуция `Co-Authored-By: Codex <noreply@openai.com>`. GitHub mutations — только в пределах разрешения владельца; `gh` использует существующую аутентификацию из macOS Keychain, Git transport — SSH.
